## Findings, most severe first

### 1. High, proven, blocking: a switched-off tab is still readable through the API

- **Contract evidence:** `docs/API_CONTRACT.md:295-297`: `GET /jobs` (including `status=completed`, `includeCancelled`), `/jobs/board-counts` and `/jobs/{jobId}` (lines, progress, corrections, attachments) use `F:eq.fleet.view|eq.jobs.view`. Same for `:356` (attachment list), EQ work evidence `:358-359` and `docs/DATA_CONTRACT.md:853` ("EQ work evidence: `eq.fleet.view` or `eq.jobs.view`"). FAC has the same pattern: `API_CONTRACT.md:571-573` serves the FAC Jobs list (`view=mywork|all`), job detail and cycles under `F:fac.jobs.view|fac.dashboard.view`; `:647` and `DATA_CONTRACT.md:1258` allow the FAC export with the dashboard feature alone.
- **Trigger:** Admin switches EQ Jobs (or FAC Jobs) off for Management or FAC Team while Fleet (or Dashboard) stays on (the default).
- **Consequence:** the server still returns the whole special-job history, corrections and evidence (or the FAC Jobs list). Contradicts APPROVED s4.2 (line 152), SOW V2 s3.2 ("A hidden tab is also blocked on the API"), ACC02 (`ACCEPTANCE_CHECKLIST.md:113`) and demo step 12 (`:183`). The crane view does not need `/jobs`: s4.16 `current-state/special` already returns its open jobs, and its links go to `/eq/jobs`, which needs `eq.jobs.view`.
- **Prototype has the same gap:** with `management|eq.jobs.view` off, the simulated `EQ.history('eq-qc-demo-01')` still returned 3 completed jobs; the crane panel still offered "Open in Jobs" and the EQJ-2026-000104 link, both leading to the 403 page (`panel-tabs.js:23,65,92`).
- **Weak supporting check:** P02B check B01 (`tools/p02b/check_p02b.mjs:85-100`) calls `EQ.access.srv()` directly, so it never tests a data read.
- **Correction:** put `/jobs` (list, board-counts, `{id}`), job attachments and EQ evidence content under `F:eq.jobs.view`; if the crane view needs a record, allow `eq.fleet.view` only for open jobs reached through current-state. Restrict the FAC Jobs list and cycles to `fac.jobs.view`; keep job detail under `fac.dashboard.view` only for the dashboard row click (SOW 5.5.7); decide explicitly whether the dashboard export counts as the dashboard's own export. Hide "Open in Jobs" and job links when `eq.jobs.view` is off. Add a prototype check that does a data read with the tab off.

### 2. Medium, proven, not blocking alone: synthetic ZMMS/status history contradicts the automatic-status design shown at U1

- `artifacts/prototypes/p02-ui/js/zmms.js:108` gives every run `businessDate: today`, including runs that ended 2-3 days ago (conflicts with DATA s15.5, BusinessDate = BusinessDay(StartedUtc)).
- `zmms.js:135-141` relabels old status rows as automatic with `runId: 8`: 9 automatic changes dated 11-22 Oct all attributed to "ZMMS sync #8", which ended 22 Oct 17:38 UTC.
- Automatic rows carry free-text reasons; DATA s3.7 says the reason is null for automatic changes.
- RTG-DEMO-06 shows Auto Maintenance with no causing job while its evaluation is `unmappedValues`, computed null; s3.7 requires causes for automatic Breakdown/Maintenance.
- 13 of today's ZMMS rows have created times later than now (`zmms.js:61-62`).
- Visible in `docs/evidence/P02B/screenshots/22-eq-jobs-eq-status.png` and `10-crane-flat-whole-maintenance.png` ("ZMMS data from 22 Oct 22:18" next to jobs created 23 Oct 08:21).
- **Consequence:** at U1 the user sees one sync changing statuses across 11 days and a Maintenance status with no cause.
- **Correction:** derive the run date from its start, attribute history rows to runs on their own dates, set automatic reasons to null, give every automatic Breakdown/Maintenance its causes, keep created times in the past.

### 3. Low, proven contract gap: Back to automatic with no computed value

`DATA_CONTRACT.md:978` (s15.7 step 6) applies "that evaluation's Computed". Evaluations skipped as `automaticDisabled` or `unmappedValues` stop before step 4, so Computed is null; as written this could set a null status, which s4.2 forbids (Unreported cannot be set again). The prototype already avoids it (`zmms.js:281`). **Correction:** step 6 uses the evaluation only when a computed value exists; otherwise the "awaiting" branch.
