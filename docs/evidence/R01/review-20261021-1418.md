## Findings, most severe first

### N1 – Low, not blocking (proven gap): full replacement on a multi-lot rope set has no usable stale-screen check

- **Evidence:** each line carries one `expectedCurrentInstallationId` (`API_CONTRACT.md:290`), but `full` mode "removes all open lots" (`DATA_CONTRACT.md:395`) and step 5 requires the position's current open installation(s) to match it (`:381`). The worked example at `:400` ends with two open lots (L1, L2).
- **Trigger:** EQ Team completes a `full` replacement at a position holding two or more open lots.
- **Consequence:** P07 must either refuse it every time (full replacement of a multi-lot rope set impossible; JOB10 fails in practice) or check only one lot (another user's partial replacement can go unnoticed). The position lock prevents corruption either way.
- **Correction:** for `full` mode on a quantity-lot position, require the expected set of open lot IDs (set equality) or `expectedLastEventSequence`. Define in DATA s5.1 step 5, s5.2, s8 and API 4.8. Add a JOB10 case: two lots, full replacement, stale request gets 409 `installation_changed`.

### N2 – Nit: same-key race on commands that lock nothing is only described for completion

- **Evidence:** API s1.5 says a same-key request "waits on the aggregate lock" (`API_CONTRACT.md:37`); `POST /jobs` has no existing row to lock. Catch-and-replay on duplicate idempotency key is described only for completion (`DATA_CONTRACT.md:384-386`).
- **Consequence:** no duplicate job (transaction rolls back), but the second response is undefined; an unhandled duplicate-key error would surface as 500.
- **Correction:** state that every idempotent command catches the duplicate-key error on `IdempotencyRecord` and replays the stored response, or returns 422.

### N3 – Nit: one error code, two statuses

`job_cancelled` is 422 on the status command (`API_CONTRACT.md:202`) but 409 in the error table (`:65`, `:68`). Pick one.

### N4 – Nit: API 4.13 and 4.14 don't state their policy

They don't say `/admin/*` writes are `EqAdmin` as 4.12 does (`API_CONTRACT.md:360`). DATA s6 and deny-by-default mean no bypass, but the endpoint table should say it.

### N5 – Nit: two correction cases unspecified

- A correction on a reopened job including `job` fields or `addLines` is disallowed (`DATA_CONTRACT.md:340`, `:425`) but has no refusal code.
- The contract implies a completed replacement job can be left with zero committed lines (s5.4 back-entry, `:408`). State whether allowed and how it is displayed.
