## Findings, most severe first

### F1 – Medium, blocking (proven contract defect): a reopened job has no rules protecting its committed replacement work

- **Evidence:** `docs/DATA_CONTRACT.md:335` and `:405`: Admin reopen sets the job back to `current` and keeps committed replacement lines and installations. The generic `pending / current` rules then apply with no exception:
  - `:328`: edit may change `target` (and `kind`, per `docs/API_CONTRACT.md:271`).
  - `:332`: cancel allowed for Admin or the EQ Team creator.
  - `:331`: completion requires at least one line for replacement jobs (also `API_CONTRACT.md:285`).
- **Triggers and consequences:**
  - **Cancel:** an EQ Team creator can cancel a reopened job holding committed replacements. The job drops out of default history and job views (J5, s9) but its installation events stay live. This bypasses the Admin-only correction path (B-09; requirement s5 "completed job cannot be cancelled" and "completed replacement cannot be silently undone").
  - **Edit:** changing kind to `repair`, or moving the target, breaks J3 and D-31 (lines only on replacement jobs, inside the job's target).
  - **Re-complete:** a reopened replacement job cannot be completed again without a new line, forcing made-up data.
  - **Duplicate lines:** a new line for a position already replaced in this job hits the unique rule (`:232`) with no defined error code.
- **Needed correction (DATA s4.1/s5.3, API 4.8):**
  - If a job holds committed, non-voided lines: refuse cancel with 409 pointing to the Admin correction path; refuse changing kind to repair; refuse target changes that leave committed lines outside the target.
  - Re-completing a reopened job: accept zero new lines; check `completedOn` against the latest committed `ReplacedOn`; return 422 `duplicate_position` for a position already committed in the job.
  - Add these cases to JOB09 and JOB12 coverage.

### F2 – Low (internal inconsistency): same-key double-click completion gets 409, not a replay

- **Evidence:** DATA s5.1 checks the idempotency record (step 1) before locking the job (step 2); the version check comes first in step 2 (`DATA_CONTRACT.md:369-375`).
- **Consequence:** two simultaneous same-key requests both find no record; the second waits for the lock, then fails the version check with 409 `version_conflict`. Contradicts the s8 table (`:455`), which promises a replay with `Idempotent-Replayed: true`. The step 7 unique-key path never triggers for completion. No data duplication, but JOB06's promised response is not delivered.
- **Correction:** re-check the idempotency record right after taking the job lock, before the version check, or use an app lock on (caller, key).

### F3 – Low (undisclosed limit against B-07)

- **Evidence:** D-32 / I2 / s5.3 refuse any installation event dated before a later event at the same position (`DATA_CONTRACT.md:209`, `:402`).
- **Consequence:** once a recent replacement exists, an older replacement at that position cannot be entered by hand except by Admin void and re-entry of the chain. B-07 allows manual entry of past work, so the limit should be stated.
- **Correction:** document the impact and a back-entry procedure (enter in date order, or Admin void/re-add), or define a way to insert earlier history.
